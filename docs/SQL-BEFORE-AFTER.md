# Before and after: the inner queries the graph replaces

The full legacy tables are in [database/mysql/schema.sql](../database/mysql/schema.sql). Generated by `bun run examples`, which runs every pair and compares the results.

## My network, 1 to 3 hops

**Question:** Who can user 1 reach by following at most three accounts?

### Before: MySQL

```sql
SELECT DISTINCT reached.id
FROM (
    -- 1 hop
    SELECT followee_id AS id
      FROM follows
     WHERE follower_id = 1
    UNION
    -- 2 hops: one inner query
    SELECT followee_id
      FROM follows
     WHERE follower_id IN (SELECT followee_id FROM follows WHERE follower_id = 1)
    UNION
    -- 3 hops: an inner query inside an inner query
    SELECT followee_id
      FROM follows
     WHERE follower_id IN (
           SELECT followee_id
             FROM follows
            WHERE follower_id IN (SELECT followee_id FROM follows WHERE follower_id = 1))
) AS reached
WHERE reached.id <> 1
ORDER BY reached.id
```

### After: Neo4j

```cypher
MATCH (me:User {id: 1})-[:FOLLOWS*1..3]->(person:User)
WHERE person <> me
RETURN DISTINCT person.id AS id
ORDER BY id
```

**What changed:** Every extra hop adds another level of nesting in SQL. In Cypher it changes one number in *1..3.

Both queries return the same 5,759 ids on the demo dataset. Timings: lab scenario `friends-network`.

## People you may know

**Question:** Who is followed by at least two people I follow, and not yet by me?

### Before: MySQL

```sql
SELECT candidate.id
FROM (
    SELECT second.followee_id AS id, COUNT(*) AS mutual
      FROM follows AS second
     WHERE second.follower_id IN (SELECT followee_id FROM follows WHERE follower_id = 1)
     GROUP BY second.followee_id
) AS candidate
WHERE candidate.mutual >= 2
  AND candidate.id <> 1
  AND candidate.id NOT IN (SELECT followee_id FROM follows WHERE follower_id = 1)
ORDER BY candidate.id
```

### After: Neo4j

```cypher
MATCH (me:User {id: 1})-[:FOLLOWS]->(mutual:User)-[:FOLLOWS]->(candidate:User)
WHERE candidate <> me
WITH me, candidate, count(mutual) AS mutualCount
WHERE mutualCount >= 2
  AND NOT EXISTS { (me)-[:FOLLOWS]->(candidate) }
RETURN candidate.id AS id
ORDER BY id
```

**What changed:** The same inner query ("whom do I follow") is written twice in SQL. The pattern states the path once. MySQL is still very fast here: two hops over a good index is cheap.

Both queries return the same 7 ids on the demo dataset. Timings: lab scenario `people-you-may-know`.

## Customers who bought this also bought

**Question:** Which products were bought by people who bought product 1?

### Before: MySQL

```sql
SELECT DISTINCT items.product_id AS id
FROM order_items AS items
WHERE items.order_id IN (
      SELECT o.id
        FROM orders AS o
       WHERE o.status <> 'cancelled'
         AND o.user_id IN (
             SELECT buyer.user_id
               FROM orders AS buyer
              WHERE buyer.status <> 'cancelled'
                AND buyer.id IN (SELECT order_id FROM order_items WHERE product_id = 1)))
  AND items.product_id <> 1
ORDER BY id
```

### After: Neo4j

```cypher
MATCH (:Product {id: 1})<-[:PURCHASED]-(buyer:User)-[:PURCHASED]->(other:Product)
WHERE other.id <> 1
RETURN DISTINCT other.id AS id
ORDER BY id
```

**What changed:** Three nested inner queries across two tables become one path: product, buyer, product.

Both queries return the same 4,994 ids on the demo dataset. Timings: lab scenario `also-bought`.

## Fraud: who shares a card, device or address with a suspect

**Question:** Which accounts are directly linked to user 101?

### Before: MySQL

```sql
SELECT u.id
FROM users AS u
WHERE u.id <> 101
  AND (
      -- same device
      EXISTS (SELECT 1 FROM orders AS theirs
               WHERE theirs.user_id = u.id AND theirs.status <> 'cancelled'
                 AND theirs.device_id IN (SELECT device_id FROM orders
                                           WHERE user_id = 101 AND status <> 'cancelled'))
      -- same payment card
      OR EXISTS (SELECT 1 FROM orders AS theirs
                  WHERE theirs.user_id = u.id AND theirs.status <> 'cancelled'
                    AND theirs.card_fingerprint IN (SELECT card_fingerprint FROM orders
                                                     WHERE user_id = 101 AND status <> 'cancelled'))
      -- same shipping address
      OR EXISTS (SELECT 1 FROM orders AS theirs
                   JOIN addresses AS a ON a.id = theirs.shipping_address_id
                  WHERE theirs.user_id = u.id AND theirs.status <> 'cancelled'
                    AND (a.street, a.city, a.zip) IN (
                        SELECT mine.street, mine.city, mine.zip
                          FROM orders AS o
                          JOIN addresses AS mine ON mine.id = o.shipping_address_id
                         WHERE o.user_id = 101 AND o.status <> 'cancelled'))
  )
ORDER BY u.id
```

### After: Neo4j

```cypher
MATCH (:User {id: 101})-[:USED_DEVICE|PAID_WITH|SHIPS_TO]->(shared)
      <-[:USED_DEVICE|PAID_WITH|SHIPS_TO]-(linked:User)
RETURN DISTINCT linked.id AS id
ORDER BY id
```

**What changed:** Device, card and address are columns in SQL, so each needs its own correlated block. As nodes they are one pattern, and a longer chain is just a longer pattern.

Both queries return the same 5 ids on the demo dataset. Timings: lab scenario `fraud-rings`.

## All products under a category

**Question:** Which products belong to Electronics or any of its sub-categories?

### Before: MySQL

```sql
SELECT p.id
FROM products AS p
WHERE p.category_id IN (
      WITH RECURSIVE tree AS (
          SELECT id FROM categories WHERE id = 1
          UNION ALL
          SELECT child.id FROM categories AS child
            JOIN tree ON child.parent_id = tree.id
      )
      SELECT id FROM tree)
ORDER BY p.id
```

### After: Neo4j

```cypher
MATCH (product:Product)-[:IN_CATEGORY]->(:Category)-[:SUBCATEGORY_OF*0..]->(:Category {id: 1})
RETURN product.id AS id
ORDER BY id
```

**What changed:** SQL needs a recursive query inside an inner query. Cypher uses *0.., and MongoDB avoids recursion entirely with the stored categoryPath array.

Both queries return the same 3,798 ids on the demo dataset. Timings: lab scenario `category-tree`.
