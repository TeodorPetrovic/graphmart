### 1. One product page

**Question:** Everything the product page shows: product, brand, category, attributes, tags and the 5 newest reviews.

**Why it hurts in tables:** The data is spread over eight tables. Attributes need the Entity-Attribute-Value workaround and every one-to-many relation becomes its own inner query.

**What changes:** The product document already contains its brand, attributes and tags. Only category and reviews need an indexed lookup.

#### MySQL: 3 joins + 3 inner queries over 8 tables
```sql
-- ? = 1, 1
SELECT p.id          AS productId,
       p.name        AS name,
       b.name        AS brand,
       c.name        AS category,
       p.price_cents AS priceCents,
       -- inner query 1: Entity-Attribute-Value rows folded back into one object
       (SELECT GROUP_CONCAT(
                 CONCAT(d.name, '=', COALESCE(
                   a.value_text,
                   CAST(CAST(a.value_number AS SIGNED) AS CHAR),
                   IF(a.value_bool = 1, 'true', 'false')))
                 ORDER BY d.name SEPARATOR ', ')
          FROM product_attributes a
          JOIN attribute_definitions d ON d.id = a.attribute_id
         WHERE a.product_id = p.id) AS attributes,
       -- inner query 2: many-to-many through a link table
       (SELECT GROUP_CONCAT(t.name ORDER BY t.name SEPARATOR ', ')
          FROM product_tags pt
          JOIN tags t ON t.id = pt.tag_id
         WHERE pt.product_id = p.id) AS tags,
       -- inner query 3: the five newest reviews with their authors
       (SELECT GROUP_CONCAT(CONCAT(recent.name, ' (', recent.rating, ')')
                 ORDER BY recent.created_at DESC, recent.id DESC SEPARATOR ', ')
          FROM (SELECT r.id, r.rating, r.created_at, u.name
                  FROM reviews r
                  JOIN users u ON u.id = r.user_id
                 WHERE r.product_id = ?
                 ORDER BY r.created_at DESC, r.id DESC
                 LIMIT 5) AS recent) AS latestReviews
FROM products p
JOIN brands b     ON b.id = p.brand_id
JOIN categories c ON c.id = p.category_id
WHERE p.id = ?
```
- EAV values live in three typed columns, so reading one attribute needs COALESCE.

**Plan:** Rows read by access operators: 29 · Indexes used: PRIMARY, ix_reviews_product_created · Full table scans: recent

#### MongoDB: One document + 2 indexed lookups
```javascript
db.products.aggregate([
  { $match: { _id: 1 } },
  {
    $lookup: { from: "categories", localField: "categoryId", foreignField: "_id", as: "category" }
  },
  {
    $lookup: {
      from: "reviews",
      localField: "_id",
      foreignField: "productId",
      pipeline: [{ $sort: { createdAt: -1, _id: -1 } }, { $limit: 5 }],
      as: "reviews"
    }
  },
  {
    $project: {
      _id: 0,
      productId: "$_id",
      name: 1,
      brand: 1,
      category: { $first: "$category.name" },
      priceCents: 1,
      attributes: {
        $reduce: {
          input: {
            $map: {
              input: { $sortArray: { input: "$attributes", sortBy: { k: 1 } } },
              in: { $concat: ["$$this.k", "=", { $toString: "$$this.v" }] }
            }
          },
          initialValue: "",
          in: {
            $concat: ["$$value", { $cond: [{ $eq: ["$$value", ""] }, "", ", "] }, "$$this"]
          }
        }
      },
      tags: {
        $reduce: {
          input: { $sortArray: { input: "$tags", sortBy: 1 } },
          initialValue: "",
          in: {
            $concat: ["$$value", { $cond: [{ $eq: ["$$value", ""] }, "", ", "] }, "$$this"]
          }
        }
      },
      latestReviews: {
        $reduce: {
          input: {
            $map: {
              input: "$reviews",
              in: { $concat: ["$$this.userName", " (", { $toString: "$$this.rating" }, ")"] }
            }
          },
          initialValue: "",
          in: {
            $concat: ["$$value", { $cond: [{ $eq: ["$$value", ""] }, "", ", "] }, "$$this"]
          }
        }
      }
    }
  }
])
```
- The $match uses _id; the review lookup uses the { productId, createdAt } index.

**Plan:** Documents examined: 7 · Index keys examined: 7 · Indexes used: _id_, productId_1_createdAt_-1__id_-1 · Collection scan: no

### 2. Filter several flexible attributes

**Question:** Which laptops meet a memory, color and Wi-Fi requirement?

**Why it hurts in tables:** EAV turns each attribute condition into another indexed self-join.

**What changes:** The attribute pattern keeps related key/value pairs together and supports same-element predicates.

#### MySQL: Three indexed EAV self joins
```sql
-- ? = 16, black, 3
SELECT p.id AS productId, p.name, b.name AS brand, p.price_cents AS priceCents
FROM product_attributes ram
JOIN attribute_definitions ramDef ON ramDef.id = ram.attribute_id AND ramDef.name = 'ram_gb'
JOIN products p ON p.id = ram.product_id
JOIN product_attributes color ON color.product_id = p.id
JOIN attribute_definitions colorDef ON colorDef.id = color.attribute_id AND colorDef.name = 'color'
JOIN product_attributes wifi ON wifi.product_id = p.id
JOIN attribute_definitions wifiDef ON wifiDef.id = wifi.attribute_id AND wifiDef.name = 'wifi6'
JOIN brands b ON b.id = p.brand_id
WHERE ram.value_number >= ?
  AND color.value_text = ?
  AND wifi.value_bool = 1
  AND p.category_id = ?
ORDER BY p.id
```
- Each alias has a different indexed attribute predicate.
- The product category and id are returned from the matching rows.

**Plan:** Rows read by access operators: 2,079 · Indexes used: ix_pa_text, PRIMARY · Full table scans: none

#### MongoDB: Attribute pattern with $all
```javascript
db.products.aggregate([
  {
    $match: {
      categoryPath: 3,
      attributes: {
        $all: [
          { $elemMatch: { k: "ram_gb", v: { $gte: 16 } } },
          { $elemMatch: { k: "color", v: "black" } },
          { $elemMatch: { k: "wifi6", v: true } }
        ]
      }
    }
  },
  { $project: { _id: 0, productId: "$_id", name: 1, brand: 1, priceCents: 1 } },
  { $sort: { productId: 1 } }
])
```
- Each $elemMatch binds a key and its value to one array element.
- categoryPath is indexed and includes the laptop category.

**Plan:** Documents examined: 453 · Index keys examined: 453 · Indexes used: attributes.k_1_attributes.v_1 · Collection scan: no

### 3. Read an order history

**Question:** What line items did one customer order, newest first?

**Why it hurts in tables:** The read joins each indexed order to a separate item table.

**What changes:** An order embeds its purchased item snapshots, avoiding a join for this customer history.

#### MySQL: Order index + item join
```sql
-- ? = 1
SELECT o.id AS orderId, o.created_at AS createdAt, oi.line_no AS lineNo,
       oi.product_id AS productId, oi.product_name AS name,
       oi.unit_price_cents AS unitPriceCents, oi.quantity
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE o.user_id = ?
  AND o.status <> 'cancelled'
ORDER BY o.created_at DESC, o.id DESC, oi.line_no
```
- The filter starts at ix_orders_user_created.
- Cancelled orders are excluded and lines have a stable line number.

**Plan:** Rows read by access operators: 72 · Indexes used: ix_orders_user_created, PRIMARY · Full table scans: none

#### MongoDB: Orders with embedded items
```javascript
db.orders.aggregate([
  { $match: { userId: 1, status: { $ne: "cancelled" } } },
  { $sort: { createdAt: -1, _id: -1 } },
  { $unwind: { path: "$items", includeArrayIndex: "itemIndex" } },
  {
    $project: {
      _id: 0,
      orderId: "$_id",
      createdAt: 1,
      lineNo: { $add: ["$itemIndex", 1] },
      productId: "$items.productId",
      name: "$items.name",
      unitPriceCents: "$items.unitPriceCents",
      quantity: "$items.quantity"
    }
  },
  { $sort: { createdAt: -1, orderId: -1, lineNo: 1 } }
])
```
- The userId/createdAt index serves this history read.
- Items remain embedded in their order snapshots.

### 4. Compute search facets

**Question:** Which brands, price bands and warranty values appear in a category subtree?

**Why it hurts in tables:** The legacy schema runs separate grouped passes and first resolves the recursive category tree.

**What changes:** A materialised categoryPath selects the subtree once, then one aggregation fans out into independent facets.

#### MySQL: Recursive subtree + grouped passes
```sql
-- ? = 1
WITH RECURSIVE subtree AS (
  SELECT id FROM categories WHERE id = ?
  UNION ALL
  SELECT child.id
  FROM categories child
  JOIN subtree parent ON child.parent_id = parent.id
)
SELECT 'brand' AS facet, b.name COLLATE utf8mb4_0900_ai_ci AS value, COUNT(*) AS count
FROM products p
JOIN subtree s ON s.id = p.category_id
JOIN brands b ON b.id = p.brand_id
GROUP BY b.name
UNION ALL
SELECT 'priceBand',
       CASE WHEN p.price_cents < 5000 THEN 'under-50'
            WHEN p.price_cents < 20000 THEN '50-200'
            ELSE '200-plus' END COLLATE utf8mb4_0900_ai_ci AS band,
       COUNT(*)
FROM products p
JOIN subtree s ON s.id = p.category_id
GROUP BY band
UNION ALL
SELECT 'warranty_years', CAST(CAST(pa.value_number AS SIGNED) AS CHAR) COLLATE utf8mb4_0900_ai_ci, COUNT(*)
FROM products p
JOIN subtree s ON s.id = p.category_id
JOIN product_attributes pa ON pa.product_id = p.id
JOIN attribute_definitions ad ON ad.id = pa.attribute_id AND ad.name = 'warranty_years'
GROUP BY pa.value_number
ORDER BY facet, value
```
- The recursive CTE anchors on the selected category.
- All groups are restricted to subtree product ids.

**Plan:** Rows read by access operators: 18,589 · Indexes used: ix_categories_parent, ix_products_category_price, PRIMARY · Full table scans: s

#### MongoDB: Indexed subtree + $facet
```javascript
db.products.aggregate([
  { $match: { categoryPath: 1 } },
  {
    $facet: {
      brands: [
        { $group: { _id: "$brand", count: { $sum: 1 } } },
        { $project: { _id: 0, facet: { $literal: "brand" }, value: "$_id", count: 1 } }
      ],
      priceBands: [
        {
          $bucket: {
            groupBy: "$priceCents",
            boundaries: [0, 5000, 20000, 2147483647],
            default: "200-plus",
            output: { count: { $sum: 1 } }
          }
        },
        {
          $project: {
            _id: 0,
            facet: { $literal: "priceBand" },
            value: {
              $switch: {
                branches: [
                  { case: { $lt: ["$_id", 5000] }, then: "under-50" },
                  { case: { $lt: ["$_id", 20000] }, then: "50-200" }
                ],
                default: "200-plus"
              }
            },
            count: 1
          }
        }
      ],
      warranties: [
        { $unwind: "$attributes" },
        { $match: { "attributes.k": "warranty_years" } },
        { $group: { _id: "$attributes.v", count: { $sum: 1 } } },
        {
          $project: {
            _id: 0,
            facet: { $literal: "warranty_years" },
            value: { $toString: "$_id" },
            count: 1
          }
        }
      ]
    }
  },
  { $project: { rows: { $concatArrays: ["$brands", "$priceBands", "$warranties"] } } },
  { $unwind: "$rows" },
  { $replaceRoot: { newRoot: "$rows" } },
  { $sort: { facet: 1, value: 1 } }
])
```
- categoryPath contains the category and its ancestors.
- $facet shares the filtered input among three aggregations.

**Plan:** Documents examined: 3,798 · Index keys examined: 3,798 · Indexes used: categoryPath_1_priceCents_1 · Collection scan: no

### 5. Monthly revenue and running total

**Question:** How does non-cancelled order revenue accumulate by month?

**Why it hurts in tables:** The relational model still needs a grouped pass before the cumulative window.

**What changes:** The aggregation pipeline keeps grouping and the running window together, though MySQL may be faster for this workload.

#### MySQL: GROUP BY + window function
```sql
WITH monthly AS (
  SELECT DATE_FORMAT(created_at, '%Y-%m') AS month,
         SUM(total_cents) AS revenueCents,
         COUNT(*) AS orderCount
  FROM orders
  WHERE status <> 'cancelled'
  GROUP BY DATE_FORMAT(created_at, '%Y-%m')
)
SELECT month, revenueCents, orderCount,
       SUM(revenueCents) OVER (ORDER BY month ROWS UNBOUNDED PRECEDING) AS runningTotalCents
FROM monthly
ORDER BY month
```
- The grouped CTE feeds a cumulative SUM window.
- The order date index is available, though the whole history is needed.

**Plan:** Rows read by access operators: 100,180 · Indexes used: none · Full table scans: monthly, orders

#### MongoDB: $group + $setWindowFields
```javascript
db.orders.aggregate([
  { $match: { status: { $ne: "cancelled" } } },
  {
    $group: {
      _id: { $dateToString: { format: "%Y-%m", date: "$createdAt" } },
      revenueCents: { $sum: "$totalCents" },
      orderCount: { $sum: 1 }
    }
  },
  { $set: { month: "$_id" } },
  {
    $setWindowFields: {
      sortBy: { month: 1 },
      output: {
        runningTotalCents: { $sum: "$revenueCents", window: { documents: ["unbounded", "current"] } }
      }
    }
  },
  { $project: { _id: 0, month: 1, revenueCents: 1, orderCount: 1, runningTotalCents: 1 } },
  { $sort: { month: 1 } }
])
```
- One pipeline groups by calendar month.
- $setWindowFields computes the ordered cumulative revenue.

**Plan:** Documents examined: 97,421 · Index keys examined: 97,422 · Indexes used: status_1_createdAt_1 · Collection scan: no

### 6. Find customers above the category average

**Question:** Which customers spent above the average within this category subtree?

**Why it hurts in tables:** The nested query recomputes an aggregate over a recursively selected subtree before returning the top customers.

**What changes:** Embedded category ids and a window average keep the comparison in one pipeline, with category matches supported by an index.

#### MySQL: Recursive CTE + nested averages
```sql
-- ? = 1
WITH RECURSIVE subtree AS (
  SELECT id FROM categories WHERE id = ?
  UNION ALL
  SELECT child.id FROM categories child JOIN subtree parent ON child.parent_id = parent.id
),
customer_spend AS (
  SELECT o.user_id AS userId, SUM(oi.unit_price_cents * oi.quantity) AS spentCents
  FROM subtree s
  JOIN products p ON p.category_id = s.id
  JOIN order_items oi ON oi.product_id = p.id
  JOIN orders o ON o.id = oi.order_id
  WHERE o.status <> 'cancelled'
  GROUP BY o.user_id
)
SELECT spend.userId, u.name, spend.spentCents
FROM customer_spend spend
JOIN users u ON u.id = spend.userId
WHERE spend.spentCents > (SELECT AVG(spentCents) FROM customer_spend)
ORDER BY spend.spentCents DESC, spend.userId
LIMIT 20
```
- The subtree CTE limits products before order aggregation.
- The average is computed from the same customer spend relation.

**Plan:** Rows read by access operators: 396,858 · Indexes used: ix_categories_parent, ix_products_category_price, ix_items_product, PRIMARY · Full table scans: spend, s, customer_spend

#### MongoDB: Category lookup + average window
```javascript
db.categories.aggregate([
  { $match: { _id: 1 } },
  {
    $graphLookup: {
      from: "categories",
      startWith: "$_id",
      connectFromField: "_id",
      connectToField: "parentId",
      as: "descendants"
    }
  },
  { $set: { subtreeIds: { $concatArrays: [["$_id"], "$descendants._id"] } } },
  { $unwind: "$subtreeIds" },
  {
    $lookup: {
      from: "orders",
      let: { categoryId: "$subtreeIds" },
      localField: "subtreeIds",
      foreignField: "items.categoryId",
      pipeline: [
        { $match: { status: { $ne: "cancelled" } } },
        { $unwind: "$items" },
        { $match: { $expr: { $eq: ["$items.categoryId", "$$categoryId"] } } },
        {
          $group: {
            _id: "$userId",
            spentCents: { $sum: { $multiply: ["$items.unitPriceCents", "$items.quantity"] } }
          }
        }
      ],
      as: "categorySpenders"
    }
  },
  { $unwind: "$categorySpenders" },
  {
    $group: { _id: "$categorySpenders._id", spentCents: { $sum: "$categorySpenders.spentCents" } }
  },
  { $setWindowFields: { output: { averageSpend: { $avg: "$spentCents" } } } },
  { $match: { $expr: { $gt: ["$spentCents", "$averageSpend"] } } },
  { $sort: { spentCents: -1, _id: 1 } },
  { $limit: 20 },
  { $lookup: { from: "users", localField: "_id", foreignField: "_id", as: "customer" } },
  { $unwind: "$customer" },
  { $project: { _id: 0, userId: "$_id", name: "$customer.name", spentCents: 1 } }
])
```
- The category anchor discovers descendants.
- The indexed items.categoryId field narrows matching order lines.

**Plan:** Documents examined: 151,058 · Index keys examined: 151,058 · Indexes used: _id_, items.categoryId_1 · Collection scan: no

### 7. See the effect of the customer index

**Question:** What were this customer’s non-cancelled orders in the last seeded year?

**Why it hurts in tables:** Without the user/date index, the database must examine unrelated customers’ orders.

**What changes:** The compound user/date index narrows the read and provides its requested order.

#### MySQL: Indexed user history
```sql
-- ? = 1
SELECT id AS orderId, created_at AS createdAt, total_cents AS totalCents, status
FROM orders USE INDEX (ix_orders_user_created)
WHERE user_id = ?
  AND created_at >= '2025-11-01 00:00:00'
  AND status <> 'cancelled'
ORDER BY created_at DESC, id DESC
```
- useIndex=1 selects ix_orders_user_created.
- useIndex=0 forces MySQL to ignore that index.

**Plan:** Rows read by access operators: 11 · Indexes used: ix_orders_user_created · Full table scans: none

#### MongoDB: Compound index or natural scan
```javascript
db.orders.aggregate([
  {
    $match: {
      userId: 1,

    }

  { $sort: { createdAt: -1, _id: -1 } },

```

### 8. Walk a category subtree

**Question:** For each category below this node, how deep is it and what products does it contain?

**Why it hurts in tables:** MySQL recursively follows parent ids and aggregates each category’s directly assigned products.

**What changes:** MongoDB can traverse parent references with $graphLookup; Neo4j follows explicit category relationships.

#### MySQL: Recursive CTE
```sql
-- ? = 1
WITH RECURSIVE subtree AS (
  SELECT id, parent_id, name, 0 AS depth
  FROM categories
  WHERE id = ?
  UNION ALL
  SELECT child.id, child.parent_id, child.name, parent.depth + 1
  FROM categories child
  JOIN subtree parent ON child.parent_id = parent.id
)
SELECT subtree.id AS categoryId, subtree.depth, subtree.name,
       COUNT(p.id) AS productCount, MIN(p.price_cents) AS minPriceCents
FROM subtree
LEFT JOIN products p ON p.category_id = subtree.id
GROUP BY subtree.id, subtree.depth, subtree.name
ORDER BY subtree.depth, subtree.id
```
- The anchor is the requested category.
- The recursive term visits children and the final aggregate remains per category.

**Plan:** Rows read by access operators: 3,919 · Indexes used: ix_categories_parent, ix_products_category_price · Full table scans: subtree

#### MongoDB: $graphLookup + product lookup
```javascript
db.categories.aggregate([
  { $match: { _id: 1 } },
  {
    $graphLookup: {
      from: "categories",
      startWith: "$_id",
      connectFromField: "_id",
      connectToField: "parentId",
      depthField: "treeDepth",
      as: "descendants"
    }
  },
  {
    $project: {
      rows: {
        $concatArrays: [
          [{ _id: "$_id", name: "$name", depth: 0 }],
          {
            $map: {
              input: "$descendants",
              as: "category",
              in: {
                _id: "$$category._id",
                name: "$$category.name",
                depth: { $add: ["$$category.treeDepth", 1] }
              }
            }
          }
        ]
      }
    }
  },
  { $unwind: "$rows" },
  {
    $lookup: {
      from: "products",
      localField: "rows._id",
      foreignField: "categoryId",
      pipeline: [
        {
          $group: { _id: null, count: { $sum: 1 }, minPriceCents: { $min: "$priceCents" } }
        }
      ],
      as: "summary"
    }
  },
  {
    $project: {
      _id: 0,
      categoryId: "$rows._id",
      depth: "$rows.depth",
      name: "$rows.name",
      productCount: { $ifNull: [{ $first: "$summary.count" }, 0] },
      minPriceCents: { $ifNull: [{ $first: "$summary.minPriceCents" }, null] }
    }
  },
  { $sort: { depth: 1, categoryId: 1 } }
])
```
- The graph lookup starts from the category id.
- Products are looked up by their direct category id.

**Plan:** Documents examined: 3,799 · Index keys examined: 3,799 · Indexes used: _id_, categoryId_1 · Collection scan: no

### 9. Friends network

**Question:** How many users are first reached at each minimum follow depth?

**Why it hurts in tables:** A recursive CTE repeatedly joins the follow index and carries depth through each frontier.

**What changes:** Neo4j follows stored adjacency from one indexed user and returns the same minimum-depth counts.

#### MySQL: Recursive CTE frontier
```sql
-- ? = 1, 3
WITH RECURSIVE reachable (user_id, depth) AS (
  SELECT followee_id, 1
  FROM follows
  WHERE follower_id = ?
  UNION DISTINCT
  SELECT f.followee_id, r.depth + 1
  FROM reachable r
  JOIN follows f ON f.follower_id = r.user_id
  WHERE r.depth < ?
)
SELECT depth, COUNT(*) AS users
FROM reachable
WHERE depth = (
  SELECT MIN(inner_reachable.depth)
  FROM reachable inner_reachable
  WHERE inner_reachable.user_id = reachable.user_id
)
GROUP BY depth
ORDER BY depth
```
- The primary key on (follower_id, followee_id) serves each frontier expansion.

**Plan:** Rows read by access operators: 19,304 · Indexes used: PRIMARY, <auto_key1> · Full table scans: reachable

#### Neo4j: Bounded adjacency traversal
```cypher
// $userId = 1, $depth = 3
MATCH (source:User {id: $userId})
MATCH path = (source)-[:FOLLOWS*1..3]->(friend:User)
WITH friend, min(length(path)) AS depth
RETURN depth, count(friend) AS users
ORDER BY depth
```
- The source User lookup uses its unique id constraint.
- The planner expands only outgoing FOLLOWS relationships.

**Plan:** Total db hits: 21,290 · Rows returned: 3 · Operators: 7

### 10. People you may know

**Question:** Who is followed by at least two people I follow, excluding myself and people I already follow?

**Why it hurts in tables:** The join finds second-degree candidates, then a correlated anti-join removes existing follows.

**What changes:** The graph pattern walks two stored relationships and uses EXISTS for the anti-join.

#### MySQL: Two joins + anti-join
```sql
-- ? = 1, 1, 1
SELECT candidate.followee_id AS userId, COUNT(*) AS mutualCount
FROM follows mine
JOIN follows candidate ON candidate.follower_id = mine.followee_id
WHERE mine.follower_id = ?
  AND candidate.followee_id <> ?
  AND NOT EXISTS (
    SELECT 1 FROM follows already_followed
    WHERE already_followed.follower_id = ?
      AND already_followed.followee_id = candidate.followee_id
  )
GROUP BY candidate.followee_id
HAVING COUNT(*) >= 2
ORDER BY mutualCount DESC, userId
LIMIT 20
```
- The follows primary and reverse indexes support the two directions.

**Plan:** Rows read by access operators: 1,182 · Indexes used: PRIMARY, <auto_distinct_key> · Full table scans: none

#### Neo4j: Two-hop graph pattern
```cypher
// $userId = 1
MATCH (me:User {id: $userId})-[:FOLLOWS]->(mutual:User)-[:FOLLOWS]->(candidate:User)
WHERE candidate <> me
WITH me, candidate, count(mutual) AS mutualCount
WHERE mutualCount >= 2
  AND NOT EXISTS { (me)-[:FOLLOWS]->(candidate) }
RETURN candidate.id AS userId, mutualCount
ORDER BY mutualCount DESC, userId
LIMIT 20
```
- FOLLOWS expansion starts at the unique User id.
- EXISTS checks a single direct relationship.

**Plan:** Total db hits: 18,314 · Rows returned: 7 · Operators: 13

### 11. Also bought

**Question:** Which other products share the most distinct buyers with this product?

**Why it hurts in tables:** SQL first materializes the distinct buyer set, then uses the product-leading order item index to expand purchases.

**What changes:** Neo4j starts at the product and traverses its PURCHASED relationships to buyers and their other products.

#### MySQL: Distinct buyer set + indexed expansion
```sql
-- ? = 1, 1
WITH buyers AS (
  SELECT DISTINCT o.user_id
  FROM order_items oi
  JOIN orders o ON o.id = oi.order_id
  WHERE oi.product_id = ?
    AND o.status <> 'cancelled'
),
co_bought AS (
  SELECT oi.product_id AS productId, COUNT(DISTINCT o.user_id) AS sharedBuyers
  FROM buyers b
  JOIN orders o ON o.user_id = b.user_id AND o.status <> 'cancelled'
  JOIN order_items oi ON oi.order_id = o.id
  WHERE oi.product_id <> ?
  GROUP BY oi.product_id
)
SELECT productId, sharedBuyers
FROM co_bought
ORDER BY sharedBuyers DESC, productId
LIMIT 20
```
- The CTE restricts work to buyers of the requested product before expanding their purchases.

**Plan:** Rows read by access operators: 229,739 · Indexes used: ix_items_product, PRIMARY, ix_orders_user_created · Full table scans: co_bought, b

#### Neo4j: Product-to-buyer traversal
```cypher
// $productId = 1
MATCH (featured:Product {id: $productId})<-[:PURCHASED]-(buyer:User)
WITH featured, collect(DISTINCT buyer) AS buyers
UNWIND buyers AS buyer
MATCH (buyer)-[:PURCHASED]->(candidate:Product)
WHERE candidate <> featured
WITH candidate, count(DISTINCT buyer) AS sharedBuyers
RETURN candidate.id AS productId, sharedBuyers

LIMIT 20
```
- The unique product id anchors traversal.
- Stored PURCHASED relationships omit cancelled orders.

### 12. Social recommendations

**Question:** Which products bought by my nearby network match categories I buy from, but that I have not bought?

**Why it hurts in tables:** The recursive user frontier feeds several order, item and category joins plus an anti-join.

**What changes:** Cypher moves from the user through bounded FOLLOWS and PURCHASED adjacency, then checks category membership.

#### MySQL: Recursive network + relational joins
```sql
-- ? = 1, 2, 1, 1, 1
WITH RECURSIVE network (user_id, depth) AS (
  SELECT followee_id, 1 FROM follows WHERE follower_id = ?
  UNION DISTINCT
  SELECT f.followee_id, n.depth + 1
  FROM network n
  JOIN follows f ON f.follower_id = n.user_id
  WHERE n.depth < ?
),
network_users AS (
  SELECT DISTINCT user_id FROM network WHERE user_id <> ?
),
my_categories AS (
  SELECT DISTINCT p.category_id
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.id
  JOIN products p ON p.id = oi.product_id
  WHERE o.user_id = ? AND o.status <> 'cancelled'
),
ranked AS (
  SELECT oi.product_id AS productId, COUNT(DISTINCT o.user_id) AS score
  FROM network_users n
  JOIN orders o ON o.user_id = n.user_id AND o.status <> 'cancelled'
  JOIN order_items oi ON oi.order_id = o.id
  JOIN products p ON p.id = oi.product_id
  JOIN my_categories c ON c.category_id = p.category_id
  WHERE NOT EXISTS (
    SELECT 1 FROM orders mine
    JOIN order_items bought ON bought.order_id = mine.id
    WHERE mine.user_id = ? AND mine.status <> 'cancelled'
      AND bought.product_id = oi.product_id
  )
  GROUP BY oi.product_id
)
SELECT productId, score
FROM ranked
ORDER BY score DESC, productId
LIMIT 20
```
- Order and item indexes restrict work to reached users and their purchased products.

**Plan:** Rows read by access operators: 24,745 · Indexes used: PRIMARY, ix_orders_user_created, <auto_distinct_key>, <auto_key0> · Full table scans: ranked, n, network

#### Neo4j: Network traversal + category pattern
```cypher
// $userId = 1, $depth = 2
MATCH (me:User {id: $userId})-[:PURCHASED]->(owned:Product)-[:IN_CATEGORY]->(category:Category)
WITH me, collect(DISTINCT owned) AS myProducts, collect(DISTINCT category) AS myCategories
MATCH (me)-[:FOLLOWS*1..2]->(buyer:User)
WHERE buyer <> me
WITH DISTINCT buyer, myProducts, myCategories
MATCH (buyer)-[:PURCHASED]->(candidate:Product)-[:IN_CATEGORY]->(category:Category)
WHERE category IN myCategories
  AND NOT candidate IN myProducts
RETURN candidate.id AS productId, count(DISTINCT buyer) AS score
ORDER BY score DESC, productId
LIMIT 20
```
- The traversal is bounded from the requested user.
- My own purchases are collected once and excluded with a list check.

**Plan:** Total db hits: 105,934 · Rows returned: 20 · Operators: 16

### 13. Shortest follow path

**Question:** What is the shortest directed follow distance, up to a chosen bound?

**Why it hurts in tables:** MySQL grows a bounded recursive frontier and computes the minimum matching depth.

**What changes:** SHORTEST 1 lets Neo4j stop after finding the minimum path within the bound.

#### MySQL: Recursive BFS frontier
```sql
-- ? = 1, 5, 50
WITH RECURSIVE reachable (user_id, depth) AS (
  SELECT followee_id, 1 FROM follows WHERE follower_id = ?
  UNION DISTINCT
  SELECT f.followee_id, r.depth + 1
  FROM reachable r
  JOIN follows f ON f.follower_id = r.user_id
  WHERE r.depth < ?
)
SELECT MIN(depth) AS length
FROM reachable
WHERE user_id = ?
```
- The followee-leading primary key serves each outgoing frontier expansion.

**Plan:** Rows read by access operators: 298,714 · Indexes used: <auto_key1>, PRIMARY · Full table scans: none

#### Neo4j: SHORTEST 1 path
```cypher
// $fromId = 1, $toId = 50, $maxDepth = 5
MATCH (source:User {id: $fromId})
MATCH (target:User {id: $toId})
OPTIONAL MATCH path = SHORTEST 1 (source)-[:FOLLOWS]->{1,5}(target)
RETURN CASE WHEN path IS NULL THEN null ELSE length(path) END AS length
```
- Unique constraints anchor both endpoints.
- The shortest-path operator prunes longer candidate paths.

**Plan:** Total db hits: 138 · Rows returned: 1 · Operators: 9

### 14. Referral chain

**Question:** At each minimum referral level, how many users are there and how many units did they buy?

**Why it hurts in tables:** The recursive CTE needs an explicit visited path to survive the planted referral cycle.

**What changes:** MongoDB graphLookup and Neo4j relationship traversal follow referrals from one root while tracking discovered users.

#### MySQL: Cycle-safe recursive CTE
```sql
-- ? = 111
WITH RECURSIVE referrals (user_id, level, visited) AS (
  SELECT id, 0, CAST(CONCAT('/', id, '/') AS CHAR(2000))
  FROM users WHERE id = ?
  UNION ALL
  SELECT child.id, parent.level + 1, CONCAT(parent.visited, child.id, '/')
  FROM referrals parent
  JOIN users child ON child.referred_by_id = parent.user_id
  WHERE parent.level < 8
    AND LOCATE(CONCAT('/', child.id, '/'), parent.visited) = 0
)
SELECT r.level, COUNT(DISTINCT r.user_id) AS users,
       COALESCE(SUM(items.quantity), 0) AS units
FROM referrals r
LEFT JOIN orders o ON o.user_id = r.user_id AND o.status <> 'cancelled'
LEFT JOIN order_items items ON items.order_id = o.id
WHERE r.level > 0
GROUP BY r.level
ORDER BY r.level
```
- The indexed referred_by_id column expands one referral frontier at a time.
- A path string prevents a user from reappearing on the same traversal path.

**Plan:** Rows read by access operators: 2,371 · Indexes used: ix_users_referred_by, ix_orders_user_created, PRIMARY · Full table scans: r

#### MongoDB: $graphLookup + order lookup
```javascript
db.users.aggregate([
  { $match: { _id: 111 } },
  {
    $graphLookup: {
      from: "users",
      startWith: "$_id",
      connectFromField: "_id",
      connectToField: "referredById",
      as: "referrals",
      depthField: "depth",
      maxDepth: 7
    }
  },
  { $unwind: "$referrals" },
  { $match: { "referrals._id": { $ne: 111 } } },
  { $set: { level: { $add: ["$referrals.depth", 1] } } },
  {
    $lookup: {
      from: "orders",
      let: { referralId: "$referrals._id" },
      pipeline: [
        {
          $match: {
            $expr: {
              $and: [{ $eq: ["$userId", "$$referralId"] }, { $ne: ["$status", "cancelled"] }]
            }
          }
        },
        { $unwind: "$items" },
        { $group: { _id: null, units: { $sum: "$items.quantity" } } }
      ],
      as: "purchases"
    }
  },
  { $set: { units: { $ifNull: [{ $first: "$purchases.units" }, 0] } } },
  { $group: { _id: "$level", users: { $sum: 1 }, units: { $sum: "$units" } } },
  { $project: { _id: 0, level: "$_id", users: 1, units: 1 } },
  { $sort: { level: 1 } }
])
```
- graphLookup follows the indexed referredById relation outward.
- The lookup sums embedded item quantities for each discovered user.

**Plan:** Documents examined: 611 · Index keys examined: 611 · Indexes used: _id_, userId_1_createdAt_-1 · Collection scan: no

#### Neo4j: REFERRED adjacency traversal
```cypher
// $userId = 111
MATCH (root:User {id: $userId})
MATCH path = (root)-[:REFERRED*1..8]->(referred:User)
WHERE referred <> root
WITH referred, min(length(path)) AS level
OPTIONAL MATCH (referred)-[purchase:PURCHASED]->()
RETURN level, count(DISTINCT referred) AS users,
       coalesce(sum(purchase.quantity), 0) AS units
ORDER BY level
```
- The source id constraint anchors the traversal.
- Minimum path length assigns each user to one referral level.

**Plan:** Total db hits: 7,085 · Rows returned: 8 · Operators: 8

### 15. Fraud rings

**Question:** Which users connect to this suspect through shared devices, cards or shipping addresses, and at what minimum hop?

**Why it hurts in tables:** Three recursive SQL branches must expand device, card and address matches from each frontier user.

**What changes:** A quantified path pattern repeats the user-to-resource-to-user motif over stored relationships.

#### MySQL: Three-branch recursive CTE
```sql
-- ? = 101, 2, 2, 2, 101
WITH RECURSIVE linked (user_id, hops) AS (
  SELECT ? AS user_id, 0 AS hops
  UNION DISTINCT
  SELECT peer.user_id, current.hops + 1
  FROM linked current
  JOIN orders own ON own.user_id = current.user_id AND own.status <> 'cancelled'
  JOIN orders peer ON peer.device_id = own.device_id AND peer.status <> 'cancelled'
  WHERE current.hops < ? AND peer.user_id <> current.user_id
  UNION DISTINCT
  SELECT peer.user_id, current.hops + 1
  FROM linked current
  JOIN orders own ON own.user_id = current.user_id AND own.status <> 'cancelled'
  JOIN orders peer ON peer.card_fingerprint = own.card_fingerprint AND peer.status <> 'cancelled'
  WHERE current.hops < ? AND own.card_fingerprint IS NOT NULL
    AND peer.user_id <> current.user_id
  UNION DISTINCT
  SELECT peer.user_id, current.hops + 1
  FROM linked current
  JOIN orders own ON own.user_id = current.user_id AND own.status <> 'cancelled'
  JOIN orders peer ON peer.shipping_address_id = own.shipping_address_id AND peer.status <> 'cancelled'
  WHERE current.hops < ? AND peer.user_id <> current.user_id
)
SELECT user_id AS userId, MIN(hops) AS hops
FROM linked
WHERE hops > 0
  AND user_id <> ?
GROUP BY user_id
ORDER BY hops, userId
```
- Device, card and address branches each use their corresponding order index.
- UNION DISTINCT suppresses duplicate users at the same hop.

**Plan:** Rows read by access operators: 1,264 · Indexes used: ix_orders_user_created, ix_orders_device, ix_orders_card, ix_orders_address · Full table scans: linked

#### Neo4j: Quantified shared-resource pattern
```cypher
// $userId = 101, $hops = 2
MATCH (suspect:User {id: $userId})
MATCH path = (suspect)((left:User)-[:USED_DEVICE|PAID_WITH|SHIPS_TO]->(resource)<-[:USED_DEVICE|PAID_WITH|SHIPS_TO]-(right:User)){1,2}
WITH last(nodes(path)) AS linked, length(path) / 2 AS hops
WHERE linked <> suspect
RETURN linked.id AS userId, min(hops) AS hops
ORDER BY hops, userId
```
- The suspect id constraint anchors the repeated QPP.
- The repeated motif follows only resource links attached to the current user.

**Plan:** Total db hits: 1,014 · Rows returned: 5 · Operators: 14

### 16. Delivery route

**Question:** What is the minimum-distance route, its hop count and warehouse id sequence?

**Why it hurts in tables:** SQL expands bounded route walks and carries visited ids to prevent cycles.

**What changes:** Cypher sums each path’s relationship distances with reduce and returns the route in traversal order.

#### MySQL: Cycle-safe recursive routes
```sql
-- ? = 1, 1, 1, 8, 12
WITH RECURSIVE route_walk (warehouse_id, hops, distance, visited, route) AS (
  SELECT ?, 0, 0, CAST(CONCAT(',', ?, ',') AS CHAR(500)), CAST(? AS CHAR(500))
  UNION ALL
  SELECT edge.to_id, path.hops + 1, path.distance + edge.distance_km,
         CONCAT(path.visited, edge.to_id, ','), CONCAT(path.route, ',', edge.to_id)
  FROM route_walk path
  JOIN routes edge ON edge.from_id = path.warehouse_id
  WHERE path.hops < ?
    AND LOCATE(CONCAT(',', edge.to_id, ','), path.visited) = 0
)
SELECT distance, hops, route
FROM route_walk
WHERE warehouse_id = ?
ORDER BY distance, hops, route
LIMIT 1
```
- The routes primary key expands only outgoing edges from each current warehouse.

**Plan:** Rows read by access operators: 821 · Indexes used: <auto_key0>, PRIMARY · Full table scans: none

#### Neo4j: Bounded path + reduce
```cypher
// $fromId = 1, $toId = 12, $maxHops = 8
MATCH (source:Warehouse {id: $fromId})
MATCH (target:Warehouse {id: $toId})
MATCH path = (source)-[:ROUTE_TO*1..8]->(target)
WITH path,
     reduce(distance = 0, leg IN relationships(path) | distance + leg.distanceKm) AS distance,
     reduce(route = toString(source.id), stop IN tail(nodes(path)) | route + ',' + toString(stop.id)) AS route
RETURN distance, length(path) AS hops, route
ORDER BY distance, hops, route
LIMIT 1
```
- Warehouse id constraints anchor the path endpoints.
- reduce sums edge weights and constructs the ordered id string.

**Plan:** Total db hits: 9,651 · Rows returned: 1 · Operators: 8

### 17. Polyglot recommendation

**Question:** What are the top products bought by people I follow, excluding products I already bought?

**Why it hurts in tables:** The legacy query joins follows, orders, items, products and brands before ranking the candidates.

**What changes:** Neo4j ranks ids from relationships, then MongoDB returns product details from its document collection.

#### MySQL: Relational joins + hydration in one query
```sql
-- ? = 1, 1
SELECT candidate.id AS productId, candidate.name, brand.name AS brand,
       candidate.price_cents AS priceCents, COUNT(DISTINCT buyer.id) AS score
FROM follows f
JOIN users buyer ON buyer.id = f.followee_id
JOIN orders o ON o.user_id = buyer.id AND o.status <> 'cancelled'
JOIN order_items item ON item.order_id = o.id
JOIN products candidate ON candidate.id = item.product_id
JOIN brands brand ON brand.id = candidate.brand_id
WHERE f.follower_id = ?
  AND NOT EXISTS (
    SELECT 1 FROM orders mine
    JOIN order_items purchased ON purchased.order_id = mine.id
    WHERE mine.user_id = ? AND mine.status <> 'cancelled'
      AND purchased.product_id = candidate.id
  )
GROUP BY candidate.id, candidate.name, brand.name, candidate.price_cents
ORDER BY score DESC, productId
LIMIT 20
```
- The order and item indexes support the followed buyers and their purchases.

**Plan:** Rows read by access operators: 2,433 · Indexes used: PRIMARY, ix_orders_user_created, <auto_distinct_key> · Full table scans: none

#### Neo4j: Neo4j ranking + MongoDB hydration

WITH product, count(DISTINCT buyer) AS score
